# Research: WSL容器开发环境

**Date**: 2026-03-01
**Feature**: 001-wsl-container-dev

## 技术选型研究

### 1. TUI框架选择

| 选项 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| bubbletea | 声明式，组件化，易测试 | 学习曲线 | ✅ 采用 |
| tview | 功能丰富 | 命令式，较难测试 | 不采用 |
| termui | 简单 | 功能有限 | 不采用 |

**决策**: bubbletea
**理由**: 声明式架构，更好的测试性，与Go社区最佳实践一致

### 2. WSL2交互方式

| 选项 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| wsl.exe命令行 | 简单，稳定 | 功能有限 | ✅ 采用 |
| Windows API | 功能完整 | 复杂度高 | 不采用 |
| golang.org/x/sys | 直接系统调用 | 需要处理兼容 | 备用 |

**决策**: wsl.exe命令行 + Go标准库exec
**理由**: 足够满足需求，稳定性好

### 3. Agent SSH Server实现

| 选项 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| golang.org/x/crypto/ssh | 纯Go实现，无需额外依赖 | 需要处理密钥 | ✅ 采用 |
| 外部sshd | 功能完整 | 需要在容器中安装sshd | 不采用 |
| libssh2 | 跨平台 | C绑定 | 不采用 |

**决策**: golang.org/x/crypto/ssh
**理由**: 轻量级，不需要在容器中安装sshd，符合"不需要安装sshd"的需求

### 4. devcon集成方案

| 选项 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| exec.Command调用 | 简单，直接 | 需处理输出流 | ✅ 采用 |
| 子模块方式 | 紧耦合 | 复杂度高 | 不采用 |
| API调用 | 解耦 | 需要暴露API | 不采用 |

**决策**: exec.Command调用，输出流式到TUI
**理由**: devcon是独立工具，保持独立性，输出流式可以实时显示进度

### 5. Docker客户端

| 选项 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| docker/client | 官方SDK，功能完整 | 体积较大 | ✅ 采用 |
| docker-cli | 轻量 | 功能有限 | 备用 |
| REST API直接调用 | 无依赖 | 需要自己处理 | 不采用 |

**决策**: docker/client (docker-sdk-go)
**理由**: 官方支持，功能完整，稳定

### 6. CLI框架

| 选项 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| spf13/cobra | 成熟，自动生成帮助 | 学习曲线 | ✅ 采用 |
| urfave/cli | 简单 | 功能较少 | 不采用 |
| kingpin | 类型安全 | 不活跃 | 不采用 |

**决策**: spf13/cobra
**理由**: Go社区标准，成熟稳定，自动生成帮助文档

## 结论

| 组件 | 技术选择 | 版本 |
|------|----------|------|
| CLI框架 | spf13/cobra | v1.1.3+ |
| TUI框架 | bubbletea | v0.23.0+ |
| Docker客户端 | docker/docker | v20.10+ |
| SSH Server | golang.org/x/crypto | 最新稳定版 |
| 配置文件 | gopkg.in/yaml.v3 | v3.0.1 |
| 测试 | testing + testify | 最新 |

## 替代方案考虑

如果以上技术不可用：
- TUI降级: 使用纯fmt + ANSI转义序列
- Docker降级: 使用docker CLI + exec
- SSH降级: 使用exec直接执行系统ssh命令
